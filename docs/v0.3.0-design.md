# v0.3.0 — 设计文档 / Design Document

> 任务 DAG + TaskStore 数据层。本版**只建立数据契约,不实现调度器、不实现执行循环**。
>
> 前置版本: [v0.2.0-design.md](./v0.2.0-design.md)(三段线性 pipeline)

---

## 1. 一句话定位 / One-liner

在 v0.2.0 旁边**新增**两层模块,把"任务是什么 / 任务现在跑到哪"从 `core.pipeline` 里抽出来,作为后续单 Agent 自适应循环 + 多 Agent 协作的基础。**v0.2.0 任何代码不动**。

---

## 2. 本版目标 / Goals

```text
✓ 把 Task 的静态定义 和 运行时状态 物理分离
✓ 提供 Plan 的静态 DAG 校验
✓ 提供 TaskStore 抽象 + 单进程内存实现
✓ 提供 5 态状态机 + claim / update 语义
✗ 不实现调度器(谁决定下一步跑哪个 task)
✗ 不实现执行循环(谁真正去跑 task)
✗ 不实现多 Agent 协作(只预留 owner 字段)
✗ 不实现持久化(JSON / SQLite / 文件锁)
```

---

## 3. 为什么需要这一版 / Motivation

v0.2.0 的根本限制:**任务不是一等公民**。

| v0.2.0 表达方式 | 局限 |
|---|---|
| `Plan.steps: tuple[str, ...]` | 字符串列表,无法表达依赖 |
| `Plan.files_to_modify: tuple[str, ...]` | 扁平白名单,无法表达"先读后写" |
| `Pipeline.stages: list[StageResult]` | 流水线状态,不是任务状态 |
| `for attempt in range(3):` | 整段重试,无法单 task 重试 |
| 无 owner 概念 | 无法多 Agent 协作 |

这导致 4 类功能做不了:

```text
1. 失败单个 task 单独重试(目前只能整段重做)
2. 表达"先并行读 A、B,再合并写 C,再跑测试"(目前只能串行)
3. 多个 agent 同时跑不同 task(目前是单线程串行)
4. 实时知道"task X 现在在谁手上、跑到哪了"(目前只能从 stage 推断)
```

v0.3.0 不实现这些功能,但**把数据结构摆好**——把"调度器要操作什么"定下来,后面写调度器就只是填方法。

## 5. 数据模型 / Data Model

### 5.1 三层分离

```
┌──────────────────────────────────────────────────────────────┐
│                      TaskSpec (frozen)                       │
│  ─────────────────────────────────────────────────────────── │
│  id:           str                                           │
│  action:       str             # "read:foo.py"               │
│  depends_on:   tuple[str, ...] # 前置 task id               │
├──────────────────────────────────────────────────────────────┤
│  不变。创建后基本不再改。谁想改 → 抛 FrozenInstanceError。   │
└──────────────────────────────────────────────────────────────┘
                            ▲
┌──────────────────────────────────────────────────────────────┐
│                     TaskRuntime (可变)                       │
│  ─────────────────────────────────────────────────────────── │
│  status:  TaskStatus = PENDING                               │
│  owner:   str | None = None                                  │
├──────────────────────────────────────────────────────────────┤
│  可变。执行过程中 status / owner 会被原地改。                │
└──────────────────────────────────────────────────────────────┘
                            ▲
┌──────────────────────────────────────────────────────────────┐
│                         TaskNode                             │
│  ─────────────────────────────────────────────────────────── │
│  spec:     TaskSpec                                          │
│  runtime:  TaskRuntime                                       │
└──────────────────────────────────────────────────────────────┘
```

### 5.2 为什么这样切

按**变化频率**切:

| 字段 | 频率 | 谁来改 |
|---|---|---|
| `spec.id / action / depends_on` | 创建时定,基本不变 | 创建者(Planner 或人) |
| `runtime.status / owner` | 调度器 / Worker 每次操作都改 | 调度器 / Worker |

如果合在一起 `frozen=True` → 状态改不动;不 `frozen` → 依赖图可能被偷偷改坏。**分层是唯一能同时保住"定义不可变"和"状态可变"的方案**。

### 5.3 `Plan` = 任务集合

```python
@dataclass
class Plan:
    summary: str
    needs_code_change: bool
    tasks: dict[str, TaskNode] = field(default_factory=dict)   # key 必须 == spec.id
```

`Plan` 提供两个**纯只读**操作:
- `validate() -> None` —— 静态校验(下文 §7)
- `ready() -> list[TaskNode]` —— 当前可执行任务(下文 §8)

`Plan` **不做** mutation,**不做** 持久化。

## 6. 运行时模型 / Runtime Model

### 6.0 模块布局 / Module Layout

```text
core/task_store.py
│
├── ① module docstring                 ← 解释模块职责
├── ② from __future__ import annotations
│
├── ③ 异常层 (3 个)
│     ├── TaskNotFoundError(KeyError)         task_id 不存在
│     ├── TaskClaimError(RuntimeError)        claim 失败
│     └── InvalidTaskTransitionError          状态转移非法
│
├── ④ 抽象接口 (1 个 Protocol)
│     └── TaskStore                           6 个方法签名
│
├── ⑤ 状态机表 (2 个常量)
│     ├── _ALLOWED_TRANSITIONS                谁 → 谁 合法
│     └── _CLEAR_OWNER_ON                     哪些目标状态要清 owner
│
└── ⑥ 内存实现 (1 个类)
      └── MemoryTaskStore                      6 个方法实现
```

文件里"异常 → 接口 → 常量 → 实现"的顺序就是**读源码的顺序**:看到异常知道有什么错模式,看到接口知道能调什么,看到常量知道状态机规则,最后看实现。

### 6.1 接口全景 — `TaskStore` Protocol

```text
                        ┌──────────────────────────────────┐
                        │       TaskStore (Protocol)       │
                        └──────────────────────────────────┘
                                       │
        ┌──────────── 只读 4 个 ───────┴────────── 写 2 个 ────────────┐
        │                                                              │
   get_plan()  ─►  Plan                                          claim_task(id, owner)
   list_tasks() ─►  list[TaskNode]                                  └─► TaskNode
   list_ready() ─►  list[TaskNode]                              update_status(id, status)
   get_task(id) ─►  TaskNode                                         └─► TaskNode
```

```python
class TaskStore(Protocol):
    # 只读 4 个
    def get_plan(self) -> Plan: ...
    def list_tasks(self) -> list[TaskNode]: ...
    def list_ready(self) -> list[TaskNode]: ...
    def get_task(self, task_id: str) -> TaskNode: ...

    # 写 2 个
    def claim_task(self, task_id: str, owner: str) -> TaskNode: ...
    def update_status(self, task_id: str, status: TaskStatus) -> TaskNode: ...
```

只读 / 写清晰分组 —— 调用方一眼能看出哪些会改状态。**调用方只跟 Protocol 打交道**,换 JSON / SQLite 都不用改调用方代码。

### 6.2 `MemoryTaskStore` 内部结构

```text
┌─────────────────────────────────────────────────────────────────┐
│                      MemoryTaskStore                            │
├─────────────────────────────────────────────────────────────────┤
│  __init__(self, plan: Plan)                                     │
│     └─► self._plan = plan                                      │
│     └─► self._plan.validate()                  ← 构造即校验    │
├─────────────────────────────────────────────────────────────────┤
│  私有:_plan  (类型: Plan,持有对 task_state.Plan 的引用)         │
├─────────────────────────────────────────────────────────────────┤
│  只读 4 个方法:                                                │
│     get_plan()       ─►  self._plan                            │
│     list_tasks()     ─►  list(self._plan.tasks.values())       │
│     list_ready()     ─►  self._plan.ready()                    │
│     get_task(id)     ─►  self._plan.tasks[id]  (KeyError→...) │
├─────────────────────────────────────────────────────────────────┤
│  写 —— claim_task(id, owner)                                   │
│     ┌──────────────────────────────────────────┐                │
│     │ 1. 任务存在?           ─否─► TaskNotFoundError           │
│     │ 2. owner 非空(经strip)? ─否─► TaskClaimError("owner")    │
│     │ 3. status == PENDING?   ─否─► TaskClaimError("status")   │
│     │ 4. owner is None?       ─否─► TaskClaimError("claimed")  │
│     │ 5. 所有 deps COMPLETED? ─否─► TaskClaimError("dep")      │
│     └──────────────────────────────────────────┘                │
│     通过 → 原地改 runtime = (IN_PROGRESS, owner) → 返回 TaskNode│
├─────────────────────────────────────────────────────────────────┤
│  写 —— update_status(id, status)                                │
│     1. 任务存在?           ─否─► TaskNotFoundError              │
│     2. transition 在白名单? ─否─► InvalidTaskTransitionError   │
│     通过 → rt.status = status                                  │
│           若 status ∈ _CLEAR_OWNER_ON → rt.owner = None        │
│           返回 TaskNode                                        │
└─────────────────────────────────────────────────────────────────┘
```

**关键不变量**:构造成功的 `MemoryTaskStore`,Plan 一定是合法 DAG。所有 mutation 都在 `node.runtime` 上原地改。**只持有 `_plan` 一个引用**,从未复制。

### 6.3 claim 校验链

`claim_task` 是最容易写错的入口(同时涉及存在性 / 状态 / 所有权 / 依赖)。把 5 项校验按"**先便宜后贵**"排序:

```text
1. 任务存在?                    ─否─► TaskNotFoundError
2. owner 非空(经 strip)?        ─否─► TaskClaimError("owner must be ...")
3. status == PENDING?           ─否─► TaskClaimError("status is ..., expected 'pending'")
4. owner is None?               ─否─► TaskClaimError("already claimed by owner ...")
5. 所有 depends_on COMPLETED?   ─否─► TaskClaimError("dependencies not completed: [...]")
                                  通过 → 原地改 (status, owner) = (IN_PROGRESS, owner)
```

每步失败信息**必须包含 task_id**,方便 log 定位。前 4 步是 O(1) 字段比较,第 5 步要遍历 `depends_on`,所以放最后。

### 6.4 状态机 `_ALLOWED_TRANSITIONS`

```python
class TaskStatus(str, Enum):
    PENDING     = "pending"
    IN_PROGRESS = "in_progress"
    COMPLETED   = "completed"
    FAILED      = "failed"
    BLOCKED     = "blocked"

_ALLOWED_TRANSITIONS: dict[TaskStatus, frozenset[TaskStatus]] = {
    PENDING:     {IN_PROGRESS, BLOCKED, FAILED},
    IN_PROGRESS: {COMPLETED, FAILED, BLOCKED},
    COMPLETED:   set(),       # 终态
    FAILED:      {PENDING},   # 重试
    BLOCKED:     {PENDING},   # 重新调度
}
```

状态转移图:

```text
                       ┌────────────┐
                       │  PENDING   │  ◄─────────┐
                       └─────┬──────┘            │
              ┌──────────────┼──────────────┐    │
              │              │              │    │
              ▼              ▼              ▼    │
       ┌────────────┐  ┌────────────┐  ┌─────────┴──┐
       │IN_PROGRESS │  │  BLOCKED   │  │   FAILED   │
       └─────┬──────┘  └──────┬─────┘  └──────┬─────┘
             │                │               │
   ┌─────────┼────────┐       │               │
   ▼         ▼        ▼       │               │
┌──────┐ ┌──────┐ ┌────────┐  │               │
│COMPL │ │FAILED│ │BLOCKED │  │               │
│ETED  │ │      │ │        │  │               │
└──────┘ └──────┘ └────────┘  │               │
   终态       │        │      │               │
             └────────┴──────┴───────────────┘
              (FAILED/BLOCKED → PENDING 重试)
```

合法转移一览(完整对照 `_ALLOWED_TRANSITIONS`):

```text
PENDING     →  IN_PROGRESS / BLOCKED / FAILED
IN_PROGRESS →  COMPLETED  / FAILED    / BLOCKED
COMPLETED   →  (空,终态)
FAILED      →  PENDING  (重试)
BLOCKED     →  PENDING  (重新调度)
```

`_CLEAR_OWNER_ON = {BLOCKED, PENDING}` —— 切到这两个时自动把 `runtime.owner` 清空。

owner 处理规则:

| 切到             | owner 处理             | 理由                       |
|----------------|----------------------|--------------------------|
| `IN_PROGRESS`  | (由 `claim_task` 设)   | 正在跑,留责任归属                |
| `COMPLETED`    | **保留**               | 谁完成的                     |
| `FAILED`       | **保留**               | 谁失败的                     |
| `BLOCKED`      | **清空**               | 释放回池,别人可重新认领             |
| `PENDING`      | **清空**               | 同上                       |

### 6.5 一次典型调用的数据流

```text
caller            MemoryTaskStore                       Plan / TaskNode
  │                     │                                    │
  │  list_ready()       │                                    │
  │ ──────────────────► │  plan.ready()                     │
  │                     │ ──────────────────────────────────►│ 扫 tasks
  │ ◄────────────────── │ ◄──────────────────────────────────│ 返回 [Node]
  │ [TaskNode, ...]     │                                    │
  │                     │                                    │
  │  claim_task(id, m)  │                                    │
  │ ──────────────────► │  5 项校验(全过)                    │
  │                     │  rt.owner = "m"                    │
  │                     │  rt.status = IN_PROGRESS           │
  │ ◄────────────────── │ ◄──────(原地改 runtime)────────────│
  │ TaskNode            │                                    │
  │                     │                                    │
  │  update_status(id,  │                                    │
  │                  COMPLETED)                              │
  │ ──────────────────► │  transition 校验                   │
  │                     │  rt.status = COMPLETED             │
  │                     │  (COMPLETED ∉ _CLEAR_OWNER_ON)     │
  │                     │  → owner 保留 = "m"                │
  │ ◄────────────────── │ ◄──────────────────────────────────│
  │ TaskNode            │                                    │
```

**整张图想表达的核心**:**所有 mutation 都通过这两个写方法收敛**,其余方法只是查询;数据真正落地只动 `node.runtime` 这一个字段,从不改 `node.spec`,也从不改 `plan.tasks` 字典结构。

### 6.6 更多数据流视图 / Additional Data Flow Views

#### 6.6.1 单 step 周期 — "ready → claim → 跑 → update"

这是最基础的循环单元,所有调度器都会套这个壳:

```text
   ┌──────────────┐
   │ list_ready() │ ─────────────────────────────────────────┐
   └──────┬───────┘                                          │
          │                                                  ▼
          │ [TaskNode, ...]                          ┌─────────────────┐
          │                                          │ 取一个 node     │
          ▼                                          │ (按调度策略)    │
   ┌──────────────┐                                  └────────┬────────┘
   │ ready 是否   │ 否 ─► 检查是否全部 COMPLETED ─► 是 → 收工│
   │ 为空?        │         还有 FAILED/BLOCKED? ─► 等决策    │
   └──────┬───────┘                                          │
          │ 是                                               ▼
          ▼                                          ┌─────────────────┐
   ┌──────────────┐                                  │ claim_task(id,  │
   │ claim_task() │                                  │   owner=此agent)│
   └──────┬───────┘                                  └────────┬────────┘
          │                                                   │
          │  TaskNode (IN_PROGRESS)                           │
          ▼                                                   ▼
   ┌──────────────┐                                   ┌─────────────────┐
   │ 真去执行      │ ─── 异常 ──────────────►          │ update_status   │
   │ node.action   │                                  │ FAILED/BLOCKED  │
   └──────┬───────┘                                  └─────────────────┘
          │ 成功
          ▼
   ┌──────────────────┐
   │ update_status    │ ───► 回到顶部 list_ready()
   │ COMPLETED        │      (可能解锁新的下游 task)
   └──────────────────┘
```

#### 6.6.2 失败重试流 — "FAILED → PENDING → 重新 claim"

单 task 粒度重试,是 v0.2.0 整段重试做不到的事:

```text
   claim_task("x", "main")    ─► IN_PROGRESS, owner="main"
            │
            ▼
      跑 task x(action)
            │
   ┌────────┴────────┐
   │ 成功            │ 失败
   ▼                ▼
COMPLETED      FAILED  (owner="main" 保留)
                    │
                    ▼
            update_status("x", PENDING)   ←── 这一步是 reset
                    │                     owner 自动清空
                    ▼
              status = PENDING
              owner  = None
                    │
                    ▼
              等下次 list_ready() 看到 "x"
                    │
                    ▼
            claim_task("x", "main")     ←── 重新认领,重新跑
```

**关键观察**:FAILED → PENDING 这一步是**显式决策**,不是自动发生 —— 调度器必须自己判断"这个失败要不要重试"(永久错误就别 reset)。

#### 6.6.3 多 owner 视角 — 未来多 Agent 协作时(本版不实现)

虽然 `MemoryTaskStore` 是单进程,但 owner 字段已经预留了多 Agent 接口:

```text
   agent-A ("worker-A")        agent-B ("worker-B")
        │                            │
        ├─ list_ready()              │
        │   → [task_x, task_y]       │
        │                            │
        ├─ claim_task("x", "A")      ├─ list_ready()
        │   → IN_PROGRESS, owner=A   │   → [task_y]   ← task_x 不在了
        │                            │
        │ (在跑 task_x)              ├─ claim_task("y", "B")
        │                            │   → IN_PROGRESS, owner=B
        │                            │
        ▼                            ▼
   两个 agent 同时各跑一个,Plan.ready() 是"全局视角",
   但 store.get_task("x").owner == "A" 是"具体归属"。
```

**单进程下的非问题**:list_ready + claim_task 之间不会被插队(GIL + 同步调用)。

**多进程下的问题**:`list_ready` 看到 ready → `claim_task` 期间别的进程可能已经认走,需要原子 claim(详见 §10)。本版 owner 字段只是"接口对齐",不解决并发。

#### 6.6.4 ready 列表的"自动解锁"现象

下游任务的 ready 状态**不靠任何回调**,纯粹是被动的"上游 COMPLETED 后下次扫到时自然出现":

```text
  时刻 t0:  plan.tasks = {
              "read_foo":   PENDING
              "modify_foo": PENDING  (depends_on=("read_foo",))
              "run_tests":  PENDING  (depends_on=("modify_foo",))
           }
  plan.ready() → ["read_foo"]                     ← 只有无依赖的

  时刻 t1:  read_foo 跑完 → COMPLETED
  plan.ready() → ["modify_foo"]                   ← 依赖一解锁就出现

  时刻 t2:  modify_foo 跑完 → COMPLETED
  plan.ready() → ["run_tests"]                    ← 又解锁下一个
```

**这就是为什么 `ready()` 不需要事件 / 回调 / watcher** —— 每次现扫,纯函数语义。代价是 O(N) 扫一次,plan 大了会慢,但 v0.3.0 不考虑优化。

## 7. Plan 静态校验 / Plan.validate()

4 项检查,顺序固定:

| # | 检查 | 例 |
|---|---|---|
| 1 | 字典 key == `TaskSpec.id` | `tasks["task_a"]` 装的是 `id="task_b"` |
| 2 | 禁止自依赖 | `task_a` 的 `depends_on` 含 `"task_a"` |
| 3 | 所有依赖必须存在 | 依赖的 task_id 不在字典里 |
| 4 | 无循环依赖(DFS 三色) | a→b→c→a |

为什么按这个顺序:

1. **key/id 一致** —— 不一致时后续查依赖可能查错对象
2. **自依赖** —— 是循环的特例,先用一行 if 干掉
3. **缺依赖** —— DFS 环检测假设图闭合,缺依赖会让 DFS 静默跳过坏边
4. **DFS 环检测** —— 此时所有依赖都已存在,放心遍历

循环检测用三色 DFS(WHITE / GRAY / BLACK),命中时返回环路径用于异常信息:

```
cyclic dependency detected: a -> b -> c -> a
```

异常类型 `InvalidPlanError(ValueError)`,继承 `ValueError` 让上层可统一用 `except ValueError` 兜底。

## 8. Plan.ready() / Ready Query

只回答"现在哪些任务可以开始",**不修改任何状态**。

可执行条件(全部满足):
```
status == PENDING
owner is None
所有 depends_on.status == COMPLETED
```

关键约束:
- **不自动调 `validate()`** —— 每次调度都重跑 DAG 校验太贵,调用方构造后显式调一次
- **返回顺序 = `tasks` 字典插入顺序** —— Python 3.7+ `dict` 保证插入序,借此保证 ready 列表稳定
- **不修改 `runtime`** —— 只读,任何修改走 `TaskStore`

---

## 9. 异常分层 / Exception Hierarchy

```
KeyError                          ← Python 内置
   └── TaskNotFoundError          ← task_id 不存在

RuntimeError                      ← Python 内置
   ├── TaskClaimError             ← claim 失败(状态/owner/依赖)
   └── InvalidTaskTransitionError ← 状态转移非法
```

### 为什么 `TaskNotFoundError` 继承 `KeyError`

```python
try:
    store.get_task("ghost")
except KeyError:    # 调用方可统一用 KeyError 兜底
    ...
```

Python 标准库里 `dict.KeyError` 也是这种用法。

### 错误信息规范

每条异常**必须包含 task_id**,便于 log 定位。例:

```
cannot claim task 'b': dependencies not completed: ['a']
invalid status transition for task 'a': 'completed' -> 'in_progress'; allowed from 'completed': <none>
task 'ghost' not found in plan
```

**禁止返回 `False` / `None` 表示失败** —— 异常类型 + 信息能让调用方精确判断"为什么失败"。

## 10. 并发边界 / Concurrency Boundary

### 本轮只做单进程

```python
class MemoryTaskStore:
    """
    Concurrency:
        仅适用于单进程。list_ready() + claim_task() 在未来多进程环境下
        并不是原子操作;跨进程 TaskStore 必须通过事务或锁实现原子 claim。
    """
```

**已知非问题(单进程 + GIL + 同步调用)**:
```text
worker-A: list_ready()      → [task_x]
worker-A: claim_task("x", A) → OK
```
中间不会被插队。

**已知竞态(多进程时会出现)**:
```text
worker-A: list_ready()        → [task_x]
worker-B: list_ready()        → [task_x]   # 也看到 ready
worker-A: claim_task("x", A)  → OK
worker-B: claim_task("x", B)  → TaskClaimError("already claimed by 'A'")
```

→ 跨进程版本必须用 SQL `UPDATE ... WHERE status='pending' AND owner IS NULL` 这种原子操作,或显式加锁。本轮不实现。
