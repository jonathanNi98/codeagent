# v0.2.0 — 设计文档 / Design Document

> 当前生产版本。三段线性 LLM pipeline + Plan JSON schema + Session history + 3 层重试。
>
> 后续演进: [v0.3.0-design.md](./v0.3.0-design.md)(任务 DAG + TaskStore)

---

## 1. 一句话定位 / One-liner

用户在 REPL 里用自然语言下指令 → **Planner 出方案 → Coder 改文件 → Runner 跑测试**,全程 LLM 驱动,有 session 级记忆和 3 层自动重试。

---

## 2. 顶层架构 / Top-level Architecture

v0.2.0 —— 三段线性管道:

```text
   user_msg
      │
      ▼
┌───────────┐    ┌─────────┐    ┌─────────┐
│ Planner   │──►│  Coder   │──►│  Runner  │──► result
│ (LLM)     │    │  (LLM)   │    │  (subprocess)
└───────────┘    └─────────┘    └─────────┘
      │              │
      ▼              ▼
   读代码         改文件 + 跑测试

retry = 外面套一层 for attempt in range(3):(无状态)
```

| Stage       | 角色           | 工具                                                                    |
| ----------- | -------------- | ----------------------------------------------------------------------- |
| **Planner** | 读代码、出方案 | `list_file / read_file / search_file / run_command / git_diff`(只读 5 件) |
| **Coder**   | 按方案改文件   | 上 5 件 + `write_file`(受 `Plan.files_to_modify` 白名单约束)              |
| **Runner**  | 跑测试         | `subprocess TEST_CMD`,无 LLM                                            |

**整段是无状态的**:每个 user_msg 走完 Planner→Coder→Runner,中间不持有跨请求的状态(只有 session_history 在 main.py 模块级)。

→ 详细数据流(REPL → pipeline → 3 stages + 反馈环 + SessionTurn)见 §4.1。

## 4. 数据流 / Data Flow

### 4.1 一次完整 user_msg 的旅程

```text
1. user_msg + session_context(可选)
   └─► pipeline.run(user_msg, session_context)

2. Planner 阶段
   ├─► planner.run(user_msg, session_context)        (LLM agent loop,bound max_tool_iterations)
   │     └─► 产出 plan_text(JSON 字符串)
   ├─► plan_with_retries() 循环 3 次
   │     ├─► parse_plan(plan_text) → Plan            (Layer B:JSON 校验失败时把错注回 user_msg 重试)
   │     └─► plan.allowed_files() = frozenset(files_to_modify)
   └─► StageResult(planner, ok=True, artifact=plan_text)

3. 门控
   └─► if not plan.needs_code_change:
         return result, panel(plan.summary, "Answer")   ← 跳过 Coder + Runner

4. Coder 阶段(for attempt in 0..2,共 3 次)
   ├─► coder.run(plan_text, allowed_files, session_context, test_feedback)
   │     └─► LLM agent loop,write_file 受 allowed_files 白名单约束
   ├─► 若 attempt == 0:StageResult(coder, ok=True, artifact=code_text)
   └─► 异常 → StageResult(coder, ok=False) → return

5. Runner 阶段
   ├─► runner.run_tests()                              (subprocess,跑 TEST_CMD)
   ├─► test_passed?
   │     ├─► yes → break
   │     └─► no  → 截断 last_test_output(头 100 + 尾 500)
   │                喂回 Coder 的 test_feedback(Layer C:test → coder 重试)
   └─► StageResult(runner, ok=test.passed, artifact=test.output)

6. main.py 收尾
   └─► append SessionTurn(user_msg, plan.summary, code_text, "passed"/"failed N/M")
        → 下次启动 REPL 时注入
```

### 4.2 Session 级数据流

```text
session_history: list[SessionTurn]    ← 模块级,main.py 持有

每轮结束:
  history.append(SessionTurn(
      user_msg      = 当前指令
      plan_summary  = plan.summary 截断
      code_summary  = coder 输出摘要 截断
      test_outcome  = "passed" / "failed (attempt N/3)"
  ))

下轮启动:
  compacted = compact_history(history)         ← 3-tier 压缩
  context   = format_session_context(compacted) ← 边界标记注入
  planner.run(f"{context}\n{user_msg}", session_context=context)
```

## 5. 关键设计决策 / Key Design Decisions

### 5.1 为什么是线性 pipeline,不是 DAG

v0.2.0 把流程建模为**严格顺序的 3 个 stage**:

```
Planner → Coder → Runner
```

任意一个失败,后续 stage 直接跳过。理由:

| 决策 | 理由 |
|---|---|
| 顺序固定 | LLM 输出的 plan 是文本描述,不是结构化任务图;Coder 也不知道"哪些子任务可以并行" |
| 失败立即终止 | v0.2.0 没有 task 概念,失败 = 当前 stage 返回 ok=False,继续没意义 |
| 全程 LLM 驱动 | 3 个 stage 都用同一个 LLM,靠 prompt + 工具集合区分角色 |

**已知代价**:无法表达"读 A 和 B,然后合并,然后跑测试"这种 DAG;无法单独重试一个失败的文件修改;无法多 agent 协作。

→ 这正是 v0.3.0 要解决的。

### 5.2 为什么 `Plan` 是 JSON Schema,不是自然语言

```json
{
  "needs_code_change": true,
  "summary": "Fix off-by-one error in subtract()",
  "steps": ["Read file", "Identify bug", "Patch"],
  "files_to_modify": ["calculator.py"]
}
```

| 字段 | 作用 |
|---|---|
| `needs_code_change` | 门控开关 —— 问答类请求直接展示 summary,不进 Coder |
| `summary` | 给 Coder + UI 显示 |
| `steps` | 给 Coder 的指令列表 |
| `files_to_modify` | Coder 的 `write_file` 白名单来源 |

**为什么强制 JSON**:
- LLM 输出有 5%~30% 会"忘了不带 fence"或"加点解释",纯文本解析极脆
- 强制 4 字段后,可以做精确校验(类型 / 非空 / 字段一致)
- 失败时把错(`PlanParseError`)注回 user_msg 让 LLM 自纠(Layer B retry)

### 5.3 为什么是 3 层重试,不是 1 层

```
Layer A: API 调用失败     → SDK 内置 max_retries=3(指数退避 + jitter)
Layer B: parse_plan 失败   → plan_with_retries() 循环 3 次,把错注回 user_msg
Layer C: test 失败         → pipeline for 循环 3 次,test_feedback 喂回 Coder
```

每层管的事不同,**不能合并**:

| 层 | 管什么 | 修复方式 |
|---|---|---|
| A | 网络 / 限流 / 临时 5xx | SDK 自动重试,等够就行 |
| B | LLM 输出不符合 schema | 把校验错注回 prompt,让 LLM 自纠 |
| C | 真实代码 bug | 把测试输出喂回 Coder,让它看错修错 |

合并 → 用户拿到 5xx 网络错时,会被"假装"成 LLM 输出格式错,污染后续 retry 的 prompt。

### 5.4 为什么有 Session-level history

REPL 是长会话。用户改完 `foo.py` 后说"再改一下",如果 Planner 看不到上一轮,就要重新调研整个仓库。

3-tier compaction 设计:

```
┌─────────────────────────────────────────────────┐
│ head      第 1 轮完整 SessionTurn                │ ← 任务锚点(用户的原始意图)
├─────────────────────────────────────────────────┤
│ middle    每轮 1 行 heuristic 压缩              │ ← 用 _truncate(60) 拼一行
│           "User='fix foo' | Plan='fix off-by'   │
│            | Coder='edit 3 lines' | Tests=ok"   │
├─────────────────────────────────────────────────┤
│ recent    最近 3 轮完整 SessionTurn              │ ← 短期细节
└─────────────────────────────────────────────────┘
```

**为什么 3-tier 而不是 LLM 摘要**:避免"调 LLM 摘要"本身消耗 token + 时间 + 又引入 LLM 不确定性。本轮用 1 行 heuristic 足够支持"还记得上一轮在干什么"。

**已知代价**:
- heuristic 摘要质量粗糙,不能跨轮做复杂推理
- 没有 token 预算感知,history 涨上去就要手动 `/reset`
- 没有 LLM-based summarization,只能等 v0.3.x

### 5.5 为什么 bound agent loop + `max_tokens` guard

v0.2.0 之前的 agent loop 是 `while True:`,有两个陷阱:

1. **max_tokens 死循环** —— LLM 持续输出到 max_tokens 截断 → 永远不到 `end_turn` → 死循环
2. **未知 stop_reason** —— SDK 升级 / 异常端点可能返回新值,悄悄落进 tool 分支造成无限 tool 调用

修复:

```python
for _ in range(cfg.max_tool_iterations):    # 硬上界
    resp = call_llm(...)
    if resp.stop_reason == "end_turn":
        return extract_text(resp.content)
    if resp.stop_reason != "tool_use":
        raise AgentTurnError(...)             # max_tokens / 未知值直接炸
    # tool_use 分支
raise AgentTurnError("exhausted ...")        # 循环耗尽也炸
```

**`-> str` 类型合约现在真的成立** —— 任何路径都返回 `str` 或抛 `AgentTurnError`,不再有"悄悄返回 `None`"的可能。

### 5.6 为什么 Coder 有 REFUSAL RULE

```python
CODER_SYSTEM_PROMPT = """
  REFUSAL RULE: If the input does Not look like a numbered plan ...
  do Not call any tools. Reply with one sentence: "Not a plan, skipping coder." and stop.
"""
```

Coder 不该"基于角色描述自动改文件"。如果 LLM 拿到的不是 plan,就拒绝执行,等下一版有 task DAG 后由调度器决定。

## 6. 关键不变量 / Key Invariants

| 不变量 | 谁保证 |
|---|---|
| `Config` 不可变 | `@dataclass(frozen=True)` |
| `Plan`(v0.2.0) 不可变 | `@dataclass(frozen=True)` |
| Agent loop 必有结果或抛 `AgentTurnError` | `for _ in range(...)` + 显式 raise |
| Session history 每次启动注入 | `main.py` 模块级 + `compact_history` |
| write_file 受白名单约束 | `tools.dispatch_tool` 校验 + Coder prompt 提醒 |
| Plan JSON 合法 | `parse_plan` 校验 + `plan_with_retries` Layer B |

## 7. 已知限制 / Known Limitations

这些是 v0.2.0 显式不解决的问题(等 v0.3.0):

```text
✗ 任务以字符串列表表达,无 DAG 结构
✗ 无 task 级别状态机,只能从 test pass/fail 反推
✗ 无 owner / 认领概念,无法多 Agent 协作
✗ 失败只能整段重试,无法只重跑一个 step
✗ 无持久化,关掉 REPL session_history 就没了
✗ session_history 无 token 预算感知
✗ 无 thrash 检测(同错反复 3 次)
✗ /diff 命令还是占位
✗ 中间压缩是 heuristic,不是 LLM 摘要
```

## 8. 与未来版本的边界 / Boundary with Future Versions

| | v0.2.0(本文档) | v0.3.0(下一版) |
|---|---|---|
| 任务模型 | 字符串列表 `steps` | DAG `tasks: dict[str, TaskNode]` |
| 状态管理 | 只有 stage.ok / stage.error | TaskStatus 5 态 + TaskStore |
| 重试粒度 | 整段流水线 | 单 task |
| 多 Agent | 不支持 | owner 字段预留 |
| 持久化 | 无 | MemoryTaskStore 起步,未来 JSON / SQLite |
| 调度 | 线性 | 暂未实现,但数据结构已就绪 |

**关键不变量**:v0.3.0 **不修改** v0.2.0 任何代码,新模块并排存在,等真有调度器再讨论桥接。
